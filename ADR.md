# Architecture Decision Records

## [1]. Backend language and framework: Python + Flask
Date: 2026-10-01
Status: Decided
Context: The app is a single-user, server-rendered tool with two small domains, and it must run as one process started by `python app.py`. I decided to use Python as that is the language I feel most comfortable with.
Decision: Use Python with Flask, Jinja templates and HTML form POSTs, and access SQLite directly through Python's built-in `sqlite3` module.
Alternatives considered: Django, rejected because its ORM, admin panel, auth and migration system solve problems this app doesn't have and add many files I'd have to justify. FastAPI, rejected because it's designed for JSON APIs with async and Pydantic models, while this app renders HTML pages from forms with no client-side JavaScript.
Consequences: Flask keeps the app small and lets me organise each domain as its own Blueprint, which maps cleanly onto a future service split. The cost is that I write the SQL and table setup myself instead of getting an ORM and migrations for free.

## [2]. Keeping the Application Pipeline and Skill Gap domains independently modular
Date: 2026-10-03
Status: Decided
Context: The app has two domains (Application Pipeline and Skill Gap Tracker) that will be split into separate services in Assignment 2. The skill gap ranking needs to know which applications are still active, which is information that belongs to the pipeline.
Decision: Each domain gets its own package (`pipeline/`, `skills/`) with pure `logic.py`, SQL-only `repository.py` and its own Flask Blueprint. The only shared table is `application_skills`; the skills domain never queries `applications` directly, and instead receives the set of active application IDs from `pipeline.repository.get_active_application_ids()`, passed in by the route.
Alternatives considered: Letting the skills SQL join `application_skills` with `applications` to filter on `status = 'active'`. It's one simpler query, but it makes the skills code depend on the pipeline's table and columns, so splitting the services later would mean rewriting the skills queries.
Consequences: In a future split, `get_active_application_ids()` becomes one HTTP call from the skills service to the pipeline service, and nothing else in the skills logic changes. The cost is one extra query per skills page and slightly more wiring in the routes.

## [3]. SQLite data model: append-only stage history and a single bridge table between domains
Date: 2026-10-04
Status: Decided
Context: The pipeline needs both the current stage of each application (for the list page) and the full timeline of stage changes (for days-in-stage and conversion rates). The skills domain needs to know which skills each application requires without owning the applications themselves.
Decision: `stage_history` is append-only, with one row per stage entered, and `applications.current_stage` and `status` are stored as well so the list page doesn't have to work them out from history every time. The two domains are linked only by the `application_skills` bridge table (application_id, skill_id) with a composite primary key, and `skills.archived` is used for soft delete.
Alternatives considered: Storing only `current_stage` with no history table, rejected because conversion rates and days-in-stage need to know when each stage was entered. Storing required skills as a comma-separated text column on `applications`, rejected because it can't be counted or joined in SQL, allows duplicates and typos, and would put skills data inside the pipeline's table.
Consequences: `current_stage` can drift from history if updated alone, so `change_stage()` always writes both in one transaction. In a future split, `application_skills` moves to the skills service and keeps `application_id` as a plain ID instead of a foreign key.

## [4]. Testing approach: test-first pure logic, real temporary SQLite for repositories, thin route checks
Date: 2026-10-05
Status: Decided
Context: The assignment requires at least 70% coverage on the core business logic of both domains, and I have to be able to explain every rule on paper. The rules most likely to have bugs are the stage transitions, conversion rates and the skill priority score, not the Flask wiring.
Decision: Business rules live in pure functions in each domain's `logic.py` (no Flask, no SQL, `today` passed in as a parameter) and are written test-first with pytest, covering edge cases like stage skips, terminal states, ties and empty inputs. Repositories are tested against a real SQLite file in pytest's `tmp_path` (a fake), and routes only get a few smoke tests through Flask's test client to check the pages are wired up.
Alternatives considered: Mocking the `sqlite3` connection in repository tests, rejected because the mocks would only check that some SQL string was sent, not that the SQL is correct, and a temporary SQLite file is just as fast. Testing everything through the routes with the test client, rejected because a failing page test doesn't tell me which rule broke, and it would be slower to write edge cases that way.
Consequences: Coverage is well above the 70% bar and a failing test points straight at the broken rule. The thinner side is the templates: what the HTML looks like is only checked by a few text assertions and by using the app by hand.

## [5]. Not building automatic skill extraction from job postings
Date: 2026-10-06
Status: Decided
Context: The skill gap ranking depends on knowing which skills each application requires. Typing tags by hand is the slowest part of using the app, so the obvious feature to add was pasting a job posting (text or URL) and having the required skills detected automatically.
Decision: Skills are tagged on each application manually, choosing from my own skills list, and the app does not parse job postings in any way.
Alternatives considered: Keyword matching against my skills list, rejected because postings phrase the same skill many ways ("Postgres", "PostgreSQL", "relational databases") and also list "nice to have" skills, so the demand counts would be wrong without me checking them anyway. Sending the posting to an external AI or NLP API, rejected because it adds a runtime dependency on an outside service and an API key, which goes against keeping the app self-contained in one container, and its output would still need checking.
Consequences: Tagging takes a minute per application, but every tag is one I chose, so demand counts and priority scores are trustworthy and the skills logic stays simple and fully testable. If extraction is added later, it can sit in front of the existing `tag_application()` as a suggestion step without changing the schema or the scoring.

## [6]. The split: a pipeline service and a skills service along the ADR-2 seam
Date: 2026-11-11
Status: Decided
Context: Assignment 2 splits the monolith into services that are deployed separately, each with its own database. ADR-2 kept the Application Pipeline and Skill Gap domains in separate packages, and the only place the skills code used the pipeline was in `skills/routes.py`, through `get_active_application_ids()` and `get_application()`.
Decision: Split exactly where ADR-2 put the seam. `services/pipeline` owns `applications` and `stage_history`, and `services/skills` owns `skills`, `my_skills` and `application_skills`. As ADR-3 predicted, `application_skills` moves to skills and `application_id` becomes a plain INT with no foreign key, because `applications` is now in another database. Only two facts cross the seam, and only from skills to pipeline over HTTP: "which applications are active" (`GET /applications/active-ids`, for the gap ranking) and "does application X exist" (`GET /applications/{id}`, before tagging). Pipeline never calls skills.
Alternatives considered: Keeping one shared database for both services, rejected because each service could still read the other's tables, so the split would only be on paper and a schema change in one service could break the other. Copying the active application IDs into the skills database, rejected because the copy can be out of date and I would need a way to keep it in sync, which is more work than one HTTP call.
Consequences: ADR-2 held, so the seam did not move and only the two calls in `skills/routes.py` change, from function calls into HTTP calls. Skills now depends on pipeline being up: the gap page has to show a notice when pipeline is down, and tagging has to refuse (503) because it can no longer check the application exists. The foreign key from `application_skills` to `applications` is lost, which ADR-7 covers.

## [7]. Data and migrations: two SQL Server databases, numbered SQL files and my own migrate.py
Date: 2026-11-12
Status: Decided
Context: In Assignment 1 everything was in one SQLite file, created by `schema.sql` at startup. After the split (ADR-6) each service needs its own database, the production databases are Azure SQL, and the schema has to change while there is already data in it, so I need a way to apply schema changes once, in order, on every environment.
Decision: Each service has its own SQL Server database (`pipeline` and `skills` locally, `<prefix>-pipeline-db` and `<prefix>-skills-db` on Azure). There was no production data to move, and Assignment 1 shipped no seed data, so nothing had to be copied or seeded: the tables start empty. Schema changes are numbered `.sql` files in `services/<name>/migrations/`, applied in order by my own `migrate.py` when the container starts, and recorded in a `schema_migrations` table so each one runs only once. An applied migration is never edited; a change is always a new file.
Alternatives considered: Alembic, rejected because the app has no ORM and the SQL is already written by hand, so Alembic would add a dependency and Python migration files only to run SQL I can run myself in about 40 lines. Keeping the `CREATE TABLE IF NOT EXISTS` script from Assignment 1, rejected because it can create tables but can't change a table that already has data, and nothing records which changes were applied.
Consequences: Integrity is lost at the seam: `application_skills.application_id` no longer has a foreign key, because `applications` is in the other database. This is compensated when tagging: skills asks pipeline whether the application exists (`application_exists()`) and refuses with 503 if pipeline can't answer, so no tag is created for an application that might not exist. It is not compensated if an application is deleted: its tags would stay. I accept this because the app never deletes applications (they end as rejected, withdrawn or accepted). Recovery plan for a bad migration: each migration and its `schema_migrations` row are committed in one transaction, so a migration that fails leaves nothing behind and the container stops before serving; a migration that succeeded but was wrong is fixed by a new forward migration, never by editing the old one; as a last resort, Azure SQL point-in-time restore can bring the database back to before the migration.

## [8]. Serverless hosting on Azure: Container Apps, serverless SQL on the free offer and a storage static website
Date: 2026-11-17
Status: Decided
Context: The system has to run on Azure in my own Azure for Students subscription, cost nothing while nobody uses it, and be deployed only by the pipeline. The subscription has a Microsoft policy that only allows five regions (Germany West Central, Poland Central, Austria East, Spain Central, Switzerland North), and IE does not let students create app registrations (service principals).
Decision: Everything is in one resource group, `rg-amolins`, in Germany West Central. The two services run as Container Apps (`amolins-ieu2024-pipeline`, `amolins-ieu2024-skills`) on the Consumption plan in one environment (`amolins-ieu2024-env`), with min replicas 0 and max replicas 1. Each has its own serverless General Purpose Gen5 database (0.5 to 1 vCore) on the logical server `amolins-ieu2024-sql`, on Azure SQL's free offer (auto-pause after 60 minutes, 32 GB, and it pauses instead of billing when the monthly free amount is used up). The UI is a static website in the storage account `amolinsieu2024ui`. Images are on GHCR (public, so Container Apps can pull them without a password). The pipeline signs in through OpenID Connect as the user-assigned managed identity `amolins-ieu2024-github-id`, which has Contributor on `rg-amolins` only and trusts only runs on `main` of my repository, so no Azure password exists. Each database has one user for its own service only. I created them as contained database users (`CREATE USER ... WITH PASSWORD` inside each database), because the portal's Query editor can't open `master`, where server logins live; each user still reaches only its own database. The resource group and identity names (`rg-amolins` instead of `rg-amolins-ieu2024`, `-github-id` instead of `-github`) come from before the brief was updated; I kept them because a resource group can't be renamed and moving everything would risk the deployed data for a naming difference only, and `system.yaml` records the real names.
Alternatives considered: A Static Web App for the UI, rejected because Static Web Apps only exist in Central US, East US 2, West US 2, West Europe and East Asia, none of which my subscription allows (Azure refused with `RequestDisallowedByAzure`). Azure Container Registry, rejected because it has a fixed monthly cost and GHCR is free. Keeping one replica always running (min replicas 1), rejected because it costs money even when idle, which is exactly what scale to zero avoids. A service principal with a client secret, impossible here (no permission to create app registrations) and worse anyway, because the secret would have to be stored and rotated.
Consequences: When idle, nothing runs: no replicas, the databases pause after 60 minutes, and the storage account only stores a few files, so the cost is close to zero. The price is the cold start: the first request after a break waits for the container to start, the database to resume (up to about a minute, failing meanwhile with error 40613 or a timeout), and pending migrations to run. `connect_with_retry()` retries with backoff (2, 4, 8, 16, 30 seconds ...) so the service survives the resume. Until it is ready, Container Apps answers with 503, so the UI shows "waking up" and retries reads automatically instead of a blank page; skills uses a 10-second timeout to pipeline on Azure (2 seconds locally) because pipeline may be starting too; and the CD health check waits up to 5 minutes. Running migrations at container start is safe only because there is at most one replica, gunicorn has one worker, and CD never runs two deployments at once (`concurrency: cd`), so two copies of `migrate.py` never run against the same database. At 100x traffic I would: raise max replicas, and therefore move migrations out of container start into their own CD step that runs once before the new version rolls out; keep min replicas at 1 and disable database auto-pause (leaving the free offer for paid vCores) so users never hit a cold start; and cache the active application IDs in skills for a short time, so every gap page view doesn't call pipeline.

## [9]. Pipeline and testing: what CI gates on, a stubbed pipeline for the cross-seam test
Date: 2026-11-17
Status: Decided
Context: Every merge to `main` deploys to Azure automatically, so anything CI misses reaches the live system. The brief also asks for at least one test of the flow that crosses the seam between the two services.
Decision: CI (`ci.yml`) runs on every push and pull request. For each service it installs the pinned dependencies, runs `ruff`, and runs `pytest` with coverage against a real SQL Server 2022 container started as a GitHub Actions service, failing below 70%. A separate job validates both `openapi.yaml` files against the OpenAPI specification and `system.yaml` against the provided `system.schema.json`. Both Docker images are built on every run, and pushed to GHCR tagged with the commit SHA only on `main`. CD (`cd.yml`) starts only when CI has passed on a push to `main`, deploys those exact images, and fails unless both `/health` endpoints return 200 with the new SHA within 5 minutes. The cross-seam test (`services/skills/tests/test_cross_seam.py`) runs the real skills app against its real test database but replaces the pipeline service with a stub, using the `responses` library to intercept the HTTP calls `pipeline_client` makes. The stub plays a pipeline that says only some applications are active, one that times out, one that answers 500 or broken JSON, and one that says the application doesn't exist, and the tests check that the gap ranking counts only active applications, that the gap degrades to `pipeline_available: false`, that tagging fails closed with 503 or returns 404, and that the configured timeout is used.
Alternatives considered: Running the cross-seam test against the whole compose stack, rejected because it is slow and needs both services and SQL Server up in CI, and a real pipeline can't easily be made to time out or answer with broken JSON on demand. Testing the repositories on SQLite in memory as in Assignment 1, rejected because production is SQL Server and T-SQL is different (`OUTPUT INSERTED.id`, `IF NOT EXISTS ... INSERT`, `TOP`), so SQLite would pass SQL that fails on Azure.
Consequences: Each gate stops one kind of mistake before Azure: ruff catches style errors and unused code, tests catch broken logic and broken SQL, the coverage floor stops untested code piling up, OpenAPI and schema validation catch a broken API or system description (for example a non-secret variable without a default), the image build catches a broken Dockerfile, and the health check catches a deployment that starts but can't reach its database (it did, when a database password secret was wrong). The risk of the stub is that it can drift from the real pipeline. This is limited by `services/pipeline/openapi.yaml`, which defines the shape of both endpoints, and by pipeline's own route tests, which check the real `GET /applications/active-ids` answer. Deliberately not tested automatically: the UI JavaScript (checked by clicking through it locally and on Azure), real network latency and cold starts, and the Azure configuration itself (scale settings, secrets, CORS origin), which the post-deploy health check and the live site cover instead.

## [10]. Not building an API gateway in front of the two services
Date: 2026-11-19
Status: Decided
Context: The browser calls both services directly at two different addresses, so each service needs CORS, `config.js` needs both URLs, and the UI has to handle each service waking up from zero on its own. A gateway (one container that receives every request and forwards `/applications/...` to pipeline and `/skills/...` to skills) is the usual fix for this, and the brief lists it under §1c as a third container that is out of scope.
Decision: Don't build it. The UI keeps calling `amolins-ieu2024-pipeline` and `amolins-ieu2024-skills` directly over HTTPS, each service allows only the UI's origin (`ALLOWED_ORIGIN`), and CD writes both URLs into `config.js` on every deploy.
Alternatives considered: A third Container App running a reverse proxy (for example nginx) as the gateway, rejected because §1c forbids a third container and it would be one more thing to deploy, scale to zero and wake up, so a cold request could wait for three containers instead of one or two. Putting the routes of both services behind one of them, rejected because it would undo the split (ADR-6): one service would have to know about and forward the other's API. Azure API Management, rejected because it is another paid resource outside the allowance.
Consequences: With one user and two services, CORS is a few lines in each `app.py` and `config.js` is generated, so the cost of not having a gateway is small. What I give up: one origin for the UI (no CORS at all), one place to add authentication, rate limiting and request logging for the whole system, and the freedom to move or rename a service without regenerating the UI's config. A gateway becomes worth building when any of these appear: real users who need to sign in (the check belongs in one place, not copied into every service), a third or fourth service (every new one means another URL in `config.js` and another CORS origin to keep right), public traffic that needs rate limiting, or a need to change service addresses without redeploying the UI.
